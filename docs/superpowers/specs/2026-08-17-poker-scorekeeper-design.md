# 线下德州计分器设计规格

- 日期：2026-08-17
- 状态：已完成交互设计，等待用户审阅书面规格
- 部署目标：群晖 Container Manager（Docker）
- 使用规模：最多 50 个账号、同时在线不超过 30 人

## 1. 产品目标

构建一个内部使用、支持公网访问的线下德州现金局计分器。所有用户通过手机浏览器登录，查看当前牌局、购买筹码、完成结算并查询历史战绩。管理员负责用户和牌局管理，超级管理员额外负责高权限用户管理和抽成规则。

系统只记录牌局财务台账，不处理线上扑克、手牌过程、真实支付或资金托管。

## 2. 已确认的核心约束

- 必须登录，不开放自行注册。
- 角色为超级管理员、管理员、普通用户。
- 最多同时存在 5 场已开启但尚未完成的对局。
- 每场最多 12 名参战玩家，观战人数不限。
- 同一用户可以同时观战两场，但只能在其中一场购买筹码，直到原对局完成。
- 对局开启后使用整数元计价；默认每手 ¥300。
- 对局默认启用抽成；用户也有独立的抽成开关。
- 全局抽成默认门槛为 ¥1000、比例为 10%。门槛包含等于，即 `费用后盈亏 >= 门槛`。
- 抽成规则和用户抽成开关对进行中及结算中的对局实时生效。
- 已完成结算保存最终采用的规则和金额，之后不随设置变化重算。
- 已完成对局永久锁定，不支持重新结算或修改历史结果。
- 金额全部四舍五入到整数元。
- 普通用户只能选择自己参加过的历史对局，但可查看这些对局的全桌结算和全员汇总。
- 管理员可查看、管理所有对局；普通管理员之间可以互相接管牌局。

## 3. 技术方案

采用单容器模块化单体：

- 前端：React 移动优先 PWA。
- 后端：NestJS HTTP API。
- 实时层：NestJS WebSocket Gateway + Socket.IO。
- ORM 与迁移：Prisma。
- 数据库：MySQL。
- 头像处理：服务端验证、裁剪结果接收并重新编码为 WebP。
- 部署：一个应用 Docker 容器；群晖反向代理提供 HTTPS/WSS。

React 构建产物由 NestJS 同源提供。HTTP API、WebSocket 和静态页面使用同一个内部端口，避免两个容器、跨域和额外反向代理规则。

后端按领域拆成以下模块：

- `auth`：登录、会话、强制改密、限速。
- `users`：用户、角色、昵称、头像、逻辑删除与恢复。
- `settings`：全局抽成规则。
- `games`：对局状态、座位、观战在线状态。
- `buyins`：购买与追加式更正事件。
- `settlements`：结算草稿、费用分摊、抽成、最终锁定。
- `history`：历史详情、聚合查询。
- `realtime`：对局房间、重连快照、在线观战者。
- `uploads`：头像验证、转换、存储和清理。
- `audit`：只追加审计日志。

系统只运行一个应用实例，不引入 Redis、消息队列或微服务。当前并发规模不需要这些组件。

## 4. 部署与环境

### 4.1 数据库

数据库名：`poker_scorekeeper`

| 环境 | 主机 | 端口 |
|---|---|---:|
| 本地开发与测试 | `tianyi.wiki` | `8306` |
| 群晖生产 | `192.168.10.248` | `3306` |

数据库用户名和密码只通过未提交的环境变量提供。规格、源代码、日志和 Git 历史中不得出现明文密码。

首次实施时先只读验证数据库版本、字符集和账号权限；获得设计与实施批准后，创建：

```sql
CREATE DATABASE IF NOT EXISTS poker_scorekeeper
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
```

随后使用 Prisma migration 创建表、索引和约束。

### 4.2 群晖网络边界

- 应用容器内部监听 `3000`。
- 公网只转发 HTTPS 入口，建议只开放 TCP 443。
- 群晖反向代理终止 TLS，并转发 HTTP 与 WebSocket。
- 不向公网直接开放应用端口、头像目录或 MySQL 端口。
- 生产应用使用内网地址访问 MySQL。
- 头像目录以只面向应用容器的持久化卷挂载到 `/data/avatars`。

### 4.3 容器交付

仓库应交付：

- 多阶段 `Dockerfile`。
- 单应用服务的 `docker-compose.yml`。
- 不含真实秘密的 `.env.example`。
- 容器健康检查。
- Prisma migration 部署命令。
- 群晖反向代理、WebSocket、持久化目录和升级说明。
- 数据库与头像备份/恢复命令。

镜像应兼容常见的 `linux/amd64` 与 `linux/arm64` 群晖平台。

## 5. 账户、角色与权限

### 5.1 用户资料

每个用户包含：

- 永久唯一的登录用户名。
- 启用账号之间唯一的中文昵称。
- 密码哈希。
- 角色。
- 是否参与抽成。
- 头像类型与头像值。
- 是否必须在下次登录修改密码。
- 启用、删除和审计字段。

字段校验：

- 用户名长度 3–32，只允许英文字母、数字、点、下划线和短横线，不区分大小写判重。
- 昵称去除首尾空白后长度 1–20，支持中文；启用账号之间不区分 Unicode 规范化差异判重。
- 初始密码长度 8–128。
- 新建用户的抽成开关默认启用，创建者可以在提交前关闭。

逻辑删除后，账号立即不能登录或加入新对局；历史中的用户、昵称与头像快照继续保留。旧昵称可以由新账号使用。恢复旧账号时，如果昵称已被占用，必须先选择新昵称。用户名永久不能复用。

拥有未完成参战对局的用户不能被删除、停用或降权；必须先完成原对局。普通资料和抽成开关仍可按权限修改，并对未完成对局实时生效。

系统必须始终保留至少一个启用的超级管理员。最后一个超级管理员不能被删除、停用或降级，也不能通过删除自己绕过该限制。

### 5.2 权限矩阵

| 能力 | 超级管理员 | 管理员 | 普通用户 |
|---|---:|---:|---:|
| 创建超级管理员或管理员 | 是 | 否 | 否 |
| 创建普通用户 | 是 | 是 | 否 |
| 修改普通用户资料与抽成开关 | 是 | 是 | 否 |
| 修改管理员或超级管理员 | 是 | 否 | 否 |
| 删除、恢复用户 | 是 | 否 | 否 |
| 设置全局抽成规则 | 是 | 否 | 否 |
| 创建、开启、结束任意对局 | 是 | 是 | 否 |
| 更正任意玩家最后一笔购买 | 是 | 是 | 否 |
| 购买和更正自己的最后一笔 | 是 | 是 | 是 |
| 查看全部历史与全局汇总 | 是 | 是 | 否 |
| 查看自己参加的历史对局 | 是 | 是 | 是 |

权限由后端守卫执行，前端隐藏按钮只用于改善体验，不作为安全措施。

### 5.3 密码与会话

- 不开放注册、找回密码邮件或短信验证码。
- 首个超级管理员由部署环境变量初始化，首次登录必须改密。
- 用户可以修改自己的密码。
- 管理员可重置普通用户密码。
- 超级管理员可重置任何账号密码。
- 重置后用户下次登录必须改密。
- 修改或重置密码后撤销该账号的其他会话。
- 删除、停用或修改角色后立即撤销该账号的全部现有会话。
- 会话闲置 7 天过期，绝对最长 30 天。

### 5.4 头像

- 所有用户可选择内置通用头像或上传自定义头像。
- 支持 JPG、PNG、WebP，原文件最大 5 MB。
- 前端提供正方形裁剪。
- 服务端检查真实文件类型并统一生成 256×256 WebP。
- 文件保存到群晖持久化目录，数据库只保存受控相对路径或预设头像 ID。
- 管理员可将普通用户头像重置为默认头像；超级管理员可重置任何账号头像。
- 参战时把昵称和头像写入 `game_players` 快照，历史显示不受之后资料变更影响。

## 7. 对局生命周期

状态流：

`DRAFT → ACTIVE → SETTLING → COMPLETED`

允许的例外：

- `DRAFT` 可以直接删除，不进入历史。
- `ACTIVE` 且从未产生购买记录时可以作废。
- 已产生购买记录的对局不能作废，必须完成结算。

### 7.1 数量限制

- `ACTIVE + SETTLING` 合计最多 5 场。
- 草稿不计入五场上限。
- 每场最多 12 名 `game_players`。
- 同一用户只能在一个未完成对局中拥有 `active_player_lock`。
- 该锁在首次购买时创建，在对局完成时释放，因此结算中的玩家也不能去另一桌购买。

### 7.2 创建和开启

管理员创建对局时设置：

- 名称：自动生成类似“8月17日晚场”，允许修改；进行中的名称不能重复。
- 每手金额：默认 ¥300，必须为正整数元。
- 是否抽成：默认勾选。

开启时重新验证五场上限并记录开局时间。多个管理员同时开启时，通过同一数据库锁串行检查，不能出现第六场。

### 7.3 进行中页面

- 所有已登录用户都能看到并进入进行中的对局。
- 打开页面但未购买筹码的在线用户显示在观战区。
- 首次购买后进入环形牌桌，并分配稳定座位号。
- 自己固定显示在牌桌下方并使用金色高亮。
- 桌面中央显示开局时长、每手金额和全桌总买入。
- 玩家座位显示头像、昵称、手数和买入金额。
- 8 人以内使用标准座位卡；9–12 人自动缩小，但保持围桌布局。
- 顶部分栏在“对战区”和“购买记录”之间切换。
- 底部固定“购买筹码”按钮。

计时器根据服务端 `started_at` 和服务端时间偏移在客户端递增，不进行每秒广播。

## 8. 购买与更正

### 8.1 购买

- 快捷手数：1、2、3、5、10。
- 可手动输入 1–99 手。
- 每笔购买金额为 `手数 × 对局每手金额`。
- 首次购买创建 `game_player`、座位和 `active_player_lock`。
- 对局满 12 人或用户已在另一场参战时拒绝购买。

### 8.2 更正

- 普通用户只能更正自己最后一笔逻辑购买。
- 管理员可更正任意玩家最后一笔逻辑购买。
- 更正只允许在 `ACTIVE` 状态。
- 新手数允许为 0–99；改为 0 表示整笔误购被冲正，但原记录仍保留。
- 更正不会更新或删除原记录，而是追加 `ADJUST` 事件。
- 示例：买 5 手后改为 3 手，追加 `previous_hands=5`、`new_hands=3`、`hands_delta=-2`。
- 同一逻辑购买可以再次更正；每次都从当前有效手数变更到新手数。
- 一旦该玩家又产生新的 `BUY`，旧的逻辑购买不能再更正。

### 8.3 幂等与实时更新

- 每个写请求包含客户端生成的幂等键。
- 数据库对幂等键建立唯一约束。
- 购买或更正先在事务中提交，再广播 `game.updated`。
- 客户端只有收到服务器确认后才更新金额。
- 断网重试返回原结果，不产生重复购买。
- WebSocket 重连时获取完整对局快照，不依赖遗漏事件补齐状态。

## 9. 结束与结算

### 9.1 进入结算

管理员点击“结束对局”后必须二次确认。确认时对局从 `ACTIVE` 原子变为 `SETTLING`，记录停止游戏时间，并立即禁止购买与更正。

同时只允许一位管理员编辑结算：

- 其他管理员可以只读查看当前草稿。
- 编辑者连续 5 分钟无操作后，其他管理员可二次确认接管。
- 接管记录操作者、时间和原编辑者。

结算草稿自动保存。应用重启后可以继续。

### 9.2 第一步：录入剩余金额

顶部显示全桌总买入、已录入金额和剩余差额。

每位玩家显示：

- 总买入。
- 剩余筹码折现金额输入框。
- 输入后实时计算的牌局盈亏。

定义：

```text
买入金额 B = 有效购买总手数 × 每手金额
剩余金额 C = 管理员输入的结束筹码折现金额
牌局盈亏 G = C - B
```

所有 `C` 必须为非负整数元。只有满足以下条件才能进入下一步：

```text
ΣC = ΣB
ΣG = 0
```

### 9.3 第二步：费用与分摊

- 房费默认 ¥380。
- 其他费用默认 ¥0。
- 两种费用都必须是非负整数元。
- 其他费用大于 0 时必须填写说明。
- 房费和其他费用分别选择分摊人员。
- 每个候选人旁显示牌局盈亏，便于判断。
- 两种费用均默认勾选牌局盈利最高的玩家。
- 如果最高盈利相同，默认选择座位号较小者。
- 费用大于 0 时必须至少选择一名分摊人。

整数分摊算法：

1. `q = floor(费用 / 人数)`。
2. `r = 费用 mod 人数`。
3. 所有人先分配 `q` 元。
4. 按牌局盈亏从高到低、座位号从小到大排序，前 `r` 人各增加 1 元。

例如 ¥380 由 3 人分摊，结果为 ¥127、¥127、¥126，合计严格等于 ¥380。

### 9.4 金额术语与公式

为每位玩家定义：

```text
房费份额 R
其他费用份额 O
费用后盈亏 F = G - R - O
```

“费用后盈亏”是统一数据名称。界面按正负显示：

- `F > 0`：抽成前应收。
- `F < 0`：抽成前应付。
- `F = 0`：抽成前结清。

有效抽成条件：

```text
对局启用抽成
AND 用户启用抽成
AND F >= 当前全局抽成门槛
```

亏损或低于门槛不抽成。达到门槛后，按完整 `F` 计算，而不是只对超出门槛的部分计算。

```text
抽成 K = round_half_up(F × 抽成基点 / 10000)
最终金额 A = F - K
```

默认门槛 ¥1000、默认基点 1000，即 10%。示例：`F=¥1200` 时，`K=¥120`，`A=¥1080`。

全局门槛必须是非负整数元；抽成基点范围为 0–10000，即 0%–100%。

最终全桌校验：

```text
ΣG = 0
ΣR = 房费
ΣO = 其他费用
ΣA = -(房费 + 其他费用 + 全桌抽成)
```

### 9.5 实时规则与最终固化

- 进行中和结算草稿使用当前全局规则与当前用户抽成开关实时预览。
- 最终确认事务再次读取最新设置。
- 如果设置版本自预览后发生变化，拒绝直接提交，要求管理员刷新预览并再次确认。
- 完成时保存实际采用的门槛、比例和每位用户的抽成资格。
- 已完成结果之后不再重算。

### 9.6 第三步：完整结算预览

每位玩家必须同时突出：

- 牌局盈亏。
- 分摊房费。
- 分摊其他费用。
- 费用后盈亏，以及“抽成前应收/应付”文案。
- 抽成金额。
- 最终应收/应付。

预览页说明提交后不可修改。管理员点击“确认并永久锁定结算”后，在一个数据库事务中：

1. 重新验证状态、草稿版本、设置版本、金额与权限。
2. 创建 `settlements`。
3. 创建所有 `settlement_results`。
4. 创建费用分摊明细。
5. 将对局改为 `COMPLETED`。
6. 释放全部 `active_player_locks`。
7. 写入审计日志。

任何一步失败都整体回滚。

## 10. 历史与全员汇总

### 10.1 历史列表

- 首页默认显示最近 10 场。
- 普通用户的列表只包含自己实际购买过筹码的对局。
- 只观战、不购买不会产生历史战绩。
- 管理员可查看全部历史。
- 支持最近 10 场、最近 30 场、近 30 天、近 90 天、自定义日期和手动选择对局。

### 10.2 单局详情

单局历史详情与最终结算预览复用同一个金额组件：

- 预览模式多出永久确认按钮和警告。
- 历史模式完全只读。
- 普通用户只要参加过该局，就能查看全桌所有玩家的完整结果。
- 管理员可查看任何对局。

### 10.3 全员战绩汇总

汇总先确定对局集合，再按玩家分组逐项累加。

- 普通用户只能从自己参加过的对局中选择。
- 汇总结果包含这些对局中的所有参战玩家，不只包含当前用户。
- 管理员可以选择任意历史对局。
- 未参加某局的玩家不产生该局数据。

每位玩家显示：

- 参战场次、胜负场次。
- 累计牌局盈亏。
- 累计房费。
- 累计其他费用。
- 累计费用后盈亏。
- 累计抽成。
- 累计最终应收/应付。

支持按最终金额排序。点击玩家后显示其在所选对局中的逐局构成。

## 11. 数据模型

所有业务表使用不可猜测的公开 ID，并包含必要的创建、更新时间。金额字段使用有符号 `BIGINT` 整数元；抽成比例使用整数基点，禁止浮点计算。

### 11.1 `users`

核心字段：用户名、启用昵称、昵称历史值、密码哈希、角色、抽成开关、头像类型、头像值、启用状态、强制改密、创建人、逻辑删除时间。

约束：用户名永久唯一；启用昵称唯一；最后一个超级管理员保护由事务执行。

### 11.2 `auth_sessions`

保存会话令牌哈希、用户、到期时间、绝对到期时间、最后活动、IP、User-Agent、撤销时间。数据库泄漏时不能用令牌哈希直接登录。

### 11.3 `system_settings`

单行配置：抽成门槛、抽成基点、配置版本、修改人、修改时间。配置修改使用行锁和版本递增。

### 11.4 `games`

保存名称、每手金额、是否抽成、状态、创建人、开局时间、停止游戏时间、完成时间、结算人和状态版本。

### 11.5 `game_players`

对局与用户唯一；保存昵称/头像快照、座位号和首次买入时间。对局内座位号唯一，范围为 1–12。

### 11.6 `active_player_locks`

以用户为主键，保存未完成参战对局。数据库唯一约束保证同一用户不能同时参战两桌。

### 11.7 `buyin_events`

只追加事件表：

- 类型 `BUY` 或 `ADJUST`。
- 玩家、操作者和对局。
- 原手数、新手数、手数差值。
- 被更正的逻辑购买 ID。
- 幂等键。
- 创建时间。

原购买和所有更正形成完整审计链。

### 11.8 `settlement_drafts`

每个对局最多一份草稿，保存逐人剩余金额、两类费用、费用说明、分摊选择、编辑者租约、草稿版本和最后活动时间。草稿可以覆盖更新，不是永久账目。

### 11.9 `settlements`

每个已完成对局恰好一行：总买入、总剩余、房费、其他费用、说明、采用的抽成门槛/基点、设置版本、结算人、锁定时间和校验合计。

### 11.10 `settlement_results`

每个参战者一行：买入、剩余、牌局盈亏、房费份额、其他费用份额、费用后盈亏、抽成资格、抽成金额和最终金额。

### 11.11 `settlement_fee_allocations`

保存 `ROOM` 或 `OTHER`、玩家、分配顺序、分摊金额及是否获得余数 1 元，用于重现分摊过程。

### 11.12 `audit_logs`

只追加保存操作者、动作、对象类型和 ID、请求编号、变更前后摘要、来源 IP、User-Agent 和时间。不得保存密码、会话令牌或数据库秘密。

### 11.13 关键索引与唯一约束

- `users.normalized_username` 永久唯一。
- `users.active_normalized_nickname` 在启用账号中唯一；删除时设为 `NULL`。
- `games(status, started_at)` 支持当前对局和上限检查。
- `game_players(game_id, user_id)` 与 `game_players(game_id, seat_no)` 唯一。
- `active_player_locks.user_id` 为主键。
- `buyin_events.idempotency_key` 唯一；`(game_player_id, created_at, id)` 支持寻找最后一笔逻辑购买。
- `settlement_drafts.game_id`、`settlements.game_id` 唯一。
- `settlement_results(settlement_id, game_player_id)` 唯一。
- `settlement_fee_allocations(settlement_id, fee_type, game_player_id)` 唯一。
- `audit_logs(actor_user_id, created_at)` 与 `(entity_type, entity_id, created_at)` 建普通索引。

## 12. 实时、并发与异常恢复

### 12.1 实时房间

- 每个已开启对局对应一个 Socket.IO 房间。
- 鉴权成功并打开对局页面后加入房间。
- 观战在线状态保存在应用内存，不作为财务数据。
- 业务写入成功后广播新的对局版本。
- 客户端发现版本跳跃或重连时重新请求完整快照。

### 12.2 数据库并发

- 开启对局时锁定 `system_settings` 单行，再检查 `ACTIVE + SETTLING < 5`。
- 首次购买时锁定对局，并插入唯一 `active_player_lock`。
- 更正时锁定玩家和最后一笔逻辑购买，重新验证它仍是最后一笔。
- 结束对局时锁定 `games` 行，避免购买与结束交错成功。
- 结算草稿使用版本号和编辑租约。
- 最终结算锁定对局、草稿、设置与相关玩家记录。

所有并发冲突返回稳定错误码和最新资源版本，前端提示刷新或重试。

### 12.3 故障行为

- 数据库不可用时拒绝所有写操作并显示明确提示。
- 不把未确认的购买保存在前端当作成功账目。
- 请求结果未知时，用幂等键查询服务器最终结果。
- 应用重启后从数据库恢复对局、玩家锁、购买、草稿和时间戳。
- WebSocket 不可用时页面显示“实时连接中断”，并定期拉取快照；恢复后重新加入房间。
- 健康检查区分应用存活与数据库就绪。

## 13. 安全设计

- 密码使用 Argon2id 哈希。
- 会话 Cookie 使用 `Secure`、`HttpOnly`、`SameSite=Lax`。
- 所有写接口使用 CSRF 防护。
- 登录、密码重置和敏感管理接口限速。
- 反向代理头只信任已配置的群晖代理。
- 设置 CSP、禁止 iframe 嵌套、内容类型嗅探保护和合理的 Referrer Policy。
- 对所有输入做长度、类型、范围和权限校验。
- 上传图片读取文件签名并重新编码，禁止直接按用户文件名落盘。
- 日志脱敏，不输出密码、Cookie、令牌、数据库连接串或头像原文件。
- 所有财务与高权限操作记录审计日志。

由于数据库密码曾在对话中以明文提供，生产正式上线前建议轮换密码，再把新值仅放入群晖受控的环境变量文件。

## 14. 备份、迁移与运维

- 启动时先运行 `prisma migrate deploy`，失败则应用不启动。
- migration 必须可在空数据库和上一生产版本上重复验证。
- 升级前备份数据库与头像目录。
- 建议每天执行 SQL 备份并备份头像目录，保留最近 14 天。
- 提供恢复演练说明：新建空库、导入 SQL、恢复头像、启动同版本镜像、验证健康检查与历史金额。
- 日志采用结构化输出并设置轮转，避免填满群晖磁盘。
- 提供管理员可见的只读系统状态：应用版本、数据库状态、最后成功迁移版本，不显示秘密。

## 15. 测试与验收

### 15.1 结算单元测试

覆盖：

- 买入、剩余和牌局盈亏公式。
- 全桌牌局盈亏合计为 0。
- 门槛小于、等于和大于 ¥1000。
- 未启用对局抽成或用户抽成。
- 亏损玩家永不抽成。
- 抽成四舍五入到元。
- 多人费用分摊和余数顺序。
- 费用后盈亏、最终金额及全桌校验公式。
- 全局规则变化后强制刷新预览。

### 15.2 权限集成测试

覆盖权限矩阵中的允许与拒绝路径，尤其是：

- 管理员不能创建管理员。
- 管理员不能删除用户或修改全局规则。
- 最后一个超级管理员不能被删除、停用或降级。
- 普通用户不能查看未参加的历史对局。
- 普通用户可查看自己参加对局的全桌详情与全员汇总。
- 历史结算不可修改。

### 15.3 并发与恢复测试

- 已有四场未完成对局时，两位管理员同时开启第五场，只能一个成功且总数不超过 5。
- 同一玩家同时在两桌首次购买，只能一个成功。
- 重复幂等键不重复购买。
- 更正与新购买竞争时，不会更正旧记录。
- 购买与结束竞争时，不产生结束后的购买。
- 两位管理员争用结算编辑权和超时接管。
- 最终结算重复提交只生成一套结果。
- 应用重启后恢复活动对局与结算草稿。

### 15.4 端到端测试

使用手机视口覆盖：

- 登录、强制改密。
- 首页五场对局。
- 环形牌桌 1、8、12 人布局。
- 快捷购买、手动购买和更正链。
- 三步结算和不可逆确认。
- 历史详情与全员汇总。
- 中文昵称、预设头像、自定义上传与重置。
- iPhone Safari 和 Android Chrome 的主要流程。

### 15.5 部署验收

- Docker 镜像在目标群晖架构启动。
- 本地环境连接 `tianyi.wiki:8306`。
- 生产环境连接 `192.168.10.248:3306`。
- 空库迁移、重复部署和健康检查通过。
- 群晖反向代理下 HTTPS、WebSocket 和真实客户端 IP 正常。
- 容器重建后头像和数据库数据不丢失。
- 备份文件可以实际恢复。

## 16. 明确不在首版范围内

- 自助注册、邮箱或短信验证码。
- 聊天、通知、好友、邀请或排行榜隐私开关。
- 线上扑克、手牌记录、牌谱分析或 AI 建议。
- 真实收付款、钱包、转账或支付接口。
- 多币种或小数金额。
- 离线写账和稍后同步。
- 已完成结算的修改、撤销或重新结算。
- 多组织、多俱乐部或超过两桌的横向扩展。
- 原生 iOS/Android 应用。

## 17. 完成定义

只有同时满足以下条件才算首版完成：

1. 所有已确认功能可在手机浏览器完成。
2. 权限、金额公式、并发限制和不可变历史通过自动化测试。
3. 本地测试库和群晖生产内网库的迁移路径均验证通过。
4. Docker、反向代理、头像持久化、备份与恢复文档齐全。
5. 在目标群晖上完成一次从登录、开局、购买、结算到历史汇总的真实验收。
