# 普通用户自建对局、紧凑首页与精确胜率设计

## 状态

- 设计日期：2026-08-27
- 产品方向：已确认
- 首页方案：A「紧凑分层」
- 权限方案：统一“管理员或创建者”服务端策略
- 胜率方案：浏览器前端 Web Worker 精确穷举

## 目标

- 所有正常登录用户都能创建对局。
- 普通用户能结束、结算并最终确认自己创建的对局，但不能管理他人创建的对局。
- 首页进行中卡片明显缩短，删除多余的进入提示，同时保留整卡点击。
- 对局内和独立胜率计算器在翻牌前、翻牌、转牌、河牌都使用精确穷举。
- 胜率计算始终留在用户浏览器，不上传牌面，也不阻塞页面交互。

## 明确不做

- 不新增“主持人”等用户角色。
- 不开放普通用户删除、作废或进入超级管理员对局管理页。
- 不改变同时最多 5 场、进行中名称唯一、结算租约、审计或现有对局状态机。
- 不新增 Prisma 字段或数据库迁移；`Game.createdById` 已满足所有权判断。
- 不把牌面、计算结果或计算日志发送到 API。
- 不在 Web Worker 失败时偷偷退回随机模拟。
- 本次只提交并发布新 Docker 版本，不部署到生产服务器。

## 方案选择

### 对局权限

采用集中式策略函数，而不是在每个控制器和服务中分别拼写角色与创建者判断。

服务端把“可以管理这场对局”定义为：

```text
actor.role 是 ADMIN 或 SUPER_ADMIN
或者
actor.role 是 USER 且 game.createdById 等于 actor.id
```

所有改变对局生命周期或结算数据的接口都必须调用同一策略。控制器的角色装饰器只负责允许已登录角色抵达服务层，不能代替所有权校验。

### 首页

采用已确认的 A「紧凑分层」，保留三层信息结构，不采用更激进的单行列表。

### 胜率

采用前端 Web Worker。主线程只管理输入、加载状态和结果；Worker 导入现有 `@poker-apprentice/hand-evaluator`，使用 `equityHoldem` 穷举所有合法公共牌组合。

## 权限与数据流

### 创建对局

- `POST /api/games` 对 `USER`、`ADMIN`、`SUPER_ADMIN` 开放。
- 创建前继续锁定并重新读取当前用户，拒绝已停用或已删除账号。
- 创建参数保持现状：可选名称、每手金额、是否抽成。
- 新对局继续直接进入 `ACTIVE`，`createdById` 写入当前用户 ID。
- 全局最多 5 场、进行中名称唯一和审计记录保持不变。

### 结束与结算自己的对局

以下写操作统一允许管理员或创建者执行：

- `POST /api/games/:id/begin-settlement`
- `PUT /api/games/:id/settlement-draft`
- `POST /api/games/:id/settlement-finalize`

`GET /api/games/:id/settlement-draft` 和 `POST /api/games/:id/settlement-preview` 保持现有查看权限；它们不改变服务器状态。创建者能够使用它们完成自己的结算，但本次不收紧其他参与者已有的只读查看能力。

创建者点击“结束对局”后继续使用现有流程：

1. `ACTIVE` 进入 `SETTLING`，停止计时并禁止购买与更正。
2. 以当前操作者创建结算草稿租约。
3. 进入结算向导，填写带走金额与费用。
4. 由服务端生成预览和确认令牌。
5. 创建者确认后进入 `COMPLETED`。

管理员仍能结束任意对局，并能按现有租约规则接管结算草稿。普通用户不能接管他人草稿；即使租约过期，也不能操作他人创建的对局。

### 保持受限的操作

- 删除草稿继续只允许管理员。
- 作废进行中对局继续只允许管理员。
- 硬删除和对局管理页继续只允许超级管理员。
- 普通用户直接请求他人对局的生命周期或结算写接口时返回 `FORBIDDEN`。

### 共享合同与实时快照

`GameSnapshotDto` 增加 `createdById`。原因是 `game.updated` Socket 事件向同一房间广播同一份快照，不能在共享事件中嵌入因观看者而异的 `canManageLifecycle`。

前端只用 `createdById` 与当前会话计算按钮可见性：

```text
管理员或超级管理员
或者
当前用户 ID 等于 createdById
```

这只是界面能力提示。服务端集中式权限策略仍是唯一安全边界，前端判断不能授权任何请求。

## 前端页面

### 首页创建入口

- 所有正常登录用户都显示“创建对局”。
- 达到 5 场上限时继续显示不可用状态。
- 空列表状态同样向普通用户显示“创建一场”。

### A「紧凑分层」进行中卡片

目标高度约 150px，具体以 320px 宽度不拥挤为准。

- 删除底部“点击整张卡片进入”提示行。
- 整张卡片继续是指向对局页的链接，保留清晰的键盘焦点和触摸反馈。
- 第一行：`进行中`/`结算中` 状态、对局名称、花色装饰。
- 第二行：最多 5 个玩家头像、剩余人数提示和省略后的昵称列表。
- 第三行：每手金额、玩家人数、总买入三个紧凑数据块。
- 缩小卡片内边距、头像尺寸、行间距和数据块高度，但不把可交互目标压到 44px 以下。
- 保持现有深色、金色和绿色视觉语言。

## 前端精确胜率

### 计算范围

- 允许 2 至 9 名已选择两张手牌的玩家。
- 公共牌数量只允许 0、3、4、5。
- 所有已知牌必须唯一。
- 四种街道全部使用 `equityHoldem` 精确穷举。
- 删除业务代码对 `simulateHoldem` 和固定 10,000 样本的依赖。

### Worker 边界

新增一个专用 Worker，只接收可结构化克隆的普通对象：

```text
requestId
players: [{ id, cards }]
boardCards
```

Worker 返回：

```text
requestId
samples
players: [{ id, equityPercentage, winPercentage, tiePercentage }]
```

Worker 内部继续复用现有牌面校验、百分比换算和舍入后总权益校正。公共模块不得依赖 React 或 DOM，以便直接单元测试。

### 调用方式

- 对局内牌桌和独立胜率计算器共用同一个异步计算客户端工厂与 React Hook，但每个已挂载计算器持有自己的 Worker，不能用单例互相取消任务。
- 每次提交新牌面都生成递增 `requestId`。
- 新任务开始时，上一任务结果立即失效，并终止该计算器的旧 Worker；任何已经排队的迟到消息仍因 ID 不匹配而被丢弃。
- 页面卸载时终止 Worker 或注销该页面的请求，不能在卸载后写状态。
- 独立计算器仍由“计算胜率”按钮触发。
- 对局内牌桌在至少两名玩家手牌完整时自动触发，换牌后重新计算。

### 显示状态

- 未满足条件：沿用选择手牌/公共牌提示。
- 计算中：显示“正在精确计算…”。
- 成功：显示“精确穷举 · 共计算 X 种牌面”，并展示权益、独赢和平分。
- 失败：保留已选牌面，显示“精确计算失败，请重试”，不显示旧结果，不切换为模拟值。

## 错误与并发处理

- 所有权校验与状态转换在同一数据库事务内基于锁定后的用户和对局执行，避免账号停用、并发结束或旧版本写入绕过权限。
- 创建者与管理员同时结束同一对局时，只允许一个 `ACTIVE → SETTLING` 成功，另一请求返回现有状态冲突。
- 结算继续沿用编辑者租约、草稿版本、设置版本和确认令牌防护。
- 前端收到 `FORBIDDEN` 或状态冲突后关闭确认框并刷新快照，不假装操作成功。
- Worker 初始化、执行或消息解析失败时进入明确错误状态；绝不回落到随机模拟。

## 验证范围

### 合同与策略测试

- `GameSnapshotDto.createdById` 必填且严格解析。
- 管理员可以管理任意对局。
- 普通用户可以管理自己创建的对局。
- 普通用户不能管理他人创建的对局。
- 停用或删除的创建者不能继续写入。

### API 测试

- 普通用户创建对局并写入正确的 `createdById`。
- 普通用户完整执行自己对局的开始结算、保存、预览和最终确认。
- 普通用户对他人对局的每个写入口均得到 `FORBIDDEN`。
- 管理员原有跨对局操作、接管、并发冲突和审计行为不回归。
- 删除、作废和管理列表权限保持原状。

### 前端单元测试

- 普通用户首页存在创建入口，达到上限时不可用。
- 创建者看到“结束对局”和“继续结算”，其他普通用户看不到。
- 首页卡片没有“点击整张卡片进入”，但整卡链接仍可导航。
- Worker 精确返回已知胜负、平分和翻牌前结果。
- 快速连续换牌只接受最新请求结果。
- Worker 失败时清空旧结果并显示错误，不出现模拟结果。

### 浏览器回归

- Chromium 320×568、360×800 和 WebKit 430×932。
- 首页 A 方案无横向溢出，卡片内容不重叠，整卡链接可操作。
- 普通用户可从首页创建对局并完成自己的结算；不能操作另一普通用户创建的对局。
- 独立计算器和对局内计算器都显示精确计算状态与组合数量。
- 计算期间页面仍可响应点击、切换页签和滚动。
