# 德州计分流程收口、移动端优化与对局硬删除设计

日期：2026-08-22
状态：已完成交互讨论，待用户审阅书面规格

## 1. 背景

当前版本的核心记账能力已经完整，但创建、实时连接、结算、首页、头像和超级管理员操作之间存在明显的体验与契约断层：

- 创建对局同时提供“创建草稿”和“创建并立即开启”，后者还会再次弹窗确认；开启请求失败时可能留下用户并不需要的草稿。
- 线上入口已经由 HTTP 跳转至 HTTPS，但生产配置和内容安全策略仍声明 HTTP/WS Origin，导致登录后的 Socket.IO 房间连接被拒绝，牌局全程进入 10 秒轮询降级。
- 少量玩家时仍使用接近满屏的椭圆牌桌，玩家、总买入和核心操作的视觉优先级不足。
- 结束对局后停留在牌桌页，管理员还要再点击“进入结算”。
- 结算核对页同时存在“打开永久确认”“重新生成预览”和二次确认弹窗，流程重复。
- 结算金额同时使用“应付”和负数，历史列表还会产生 `¥-380` 这类不自然格式。
- 首页仍读取旧的 `{ games, myFinalAmount }` 历史结构，而当前 `/api/history` 返回 `{ items, final }`，因此首页把有效响应当成空历史并长期显示 0。
- 用户创建与密码重置没有默认临时密码。
- 自定义头像虽然已有裁剪、上传进度和失败后重试能力，但入口仍暴露浏览器原生文件控件；预设头像选择也缺少明确的待保存和成功反馈。
- 超级管理员没有可发现的全状态对局管理入口，也不能真实删除测试对局。

本轮采用“流程收口式改造”：同步调整前端流程、共享契约和后端事务，不采用仅改文案或仅隐藏按钮的表面修补，也不重做无关业务模块。

## 2. 目标与非目标

### 2.1 目标

1. 把创建和开启合并成一个原子动作，成功后直接进入牌桌。
2. 修复生产 HTTPS/WSS 配置错位，使实时连接在正常环境下保持安静和稳定。
3. 提升少量玩家牌桌的信息密度，并正确处理 iPhone 安全区域。
4. 结束对局后直接进入结算；核对页只保留“修改”和一次“确认结算”。
5. 统一结算与历史金额语言和符号。
6. 首页只承担当前对局入口，个人历史集中到战绩页。
7. 预填默认临时密码 `12345678`，同时保留首次登录强制改密。
8. 完成一致化头像选择、保存、裁剪、进度和失败重试体验，并替换预设头像。
9. 为超级管理员提供覆盖所有状态的真实硬删除能力。
10. 用自动化测试覆盖权限、事务、并发、移动布局和主要用户路径。

### 2.2 非目标

- 不改变买入、更正、房费分摊或抽成计算公式。
- 不增加重新结算、编辑已完成结算或恢复已硬删除对局的能力。
- 不增加支付、钱包、牌谱或离线写入。
- 不把 WebSocket Origin 校验放宽为信任任意 Host 或 Origin。
- 不把第三方头像服务作为运行时依赖。

## 3. 总体方案

采用同一轮前后端契约升级：

- `games` 模块负责原子创建并开启、全状态管理列表和硬删除事务。
- `realtime` 模块增加对局删除事件，并继续以数据库快照作为财务事实来源。
- `history` 模块明确区分个人最终金额和管理员未参战状态。
- Web 端收口创建、结束和结算流程，按路由切换普通导航与沉浸式牌局布局。
- `uploads/profile` 复用现有裁剪和上传管线，只重做选择、保存和错误反馈表面。
- 生产配置改为准确的 HTTPS 公网 Origin，由应用生成对应 WSS CSP 来源。

## 4. 创建与开启对局

### 4.1 用户流程

创建页保留名称、每手金额和是否抽成三个字段，只显示一个主按钮：

`创建并开启`

点击后：

1. 禁用按钮并显示“正在创建…”；
2. 后端在一个事务中验证管理员、活动桌数量和进行中名称唯一性；
3. 直接创建 `ACTIVE` 对局并写入 `startedAt`；
4. 返回完整牌桌快照；
5. 前端使用 `replace` 导航至 `/games/:id`。

不再显示“创建草稿”、草稿保存卡片或“确认开启对局”弹窗。请求失败时留在表单并显示服务端错误，不出现半完成的可见草稿。

### 4.2 后端语义

`POST /api/games` 的产品语义改为“创建并开启”。事务必须取得与现有开启流程相同的生命周期协调锁，然后：

- 锁定并重新验证操作者仍为启用的 `ADMIN` 或 `SUPER_ADMIN`；
- 检查 `ACTIVE + SETTLING < 5`；
- 检查规范化后的进行中名称不重复；
- 创建 `status=ACTIVE`、`startedAt=now`、`version=1` 的对局；
- 写入 `GAME_CREATED_AND_STARTED` 审计记录；
- 返回事务内快照。

原有 `POST /api/games/:id/start` 暂时保留，用于开启升级前遗留的 `DRAFT` 数据；新 UI 不再创建草稿。超级管理员可在对局管理页直接删除遗留草稿。

## 5. 牌桌、结束对局与实时连接

### 5.1 牌桌信息层级

对战区在椭圆桌上方增加紧凑摘要条：

`玩家 N 人 | 全桌总买入 ¥X | 每手 ¥X`

牌桌尺寸按人数分档：

- 1–4 人：紧凑桌，目标高度约 280–320 px；
- 5–8 人：中等桌，目标高度约 330–370 px；
- 9–12 人：完整桌，目标高度约 400–450 px，并继续使用紧凑座位排布。

玩家头像、昵称、手数和买入金额使用带半透明背景的座位信息块，提高在绿色桌面上的可读性。总买入不再只藏在桌心；桌心保留计时器作为主要信息。

### 5.2 导航与 iPhone 安全区域

`index.html` 的 viewport 增加 `viewport-fit=cover`。

普通首页、战绩和个人页继续显示三项底部导航。以下沉浸式路由隐藏全局底部导航：

- `/games/:id`
- `/games/:id/settlement`

对局页只保留“购买筹码”操作栏。该栏的底部距离直接使用 `env(safe-area-inset-bottom)`，正文底部留白等于操作栏实际高度加安全区，不再同时为全局导航和操作栏预留两份空间。结算页操作按钮进入正常文档流，不固定遮挡内容。

### 5.3 结束并进入结算

管理员点击“结束对局”后只出现一次确认，主按钮文案为：

`确认结束并进入结算`

确认成功后，前端立即导航至 `/games/:id/settlement`。不再停留在 `SETTLING` 牌桌，也不再要求点击“进入结算”。如果转换失败，确认框保留并显示可重试错误。

### 5.4 实时连接根因与修复

线上 `http://pk.tianyi.wiki` 当前由 OpenResty 跳转到 `https://pk.tianyi.wiki`，但应用响应头仍包含 `ws://pk.tianyi.wiki`，且 WebSocket Origin 白名单仍按 HTTP 配置。浏览器实际发送的 `Origin: https://pk.tianyi.wiki` 因此无法通过严格校验。

修复方式：

- 生产 `PUBLIC_ORIGIN` 改为 `https://pk.tianyi.wiki`；
- 由现有安全配置生成 `wss://pk.tianyi.wiki` CSP `connect-src`；
- OpenResty 继续正确转发 `/socket.io/` 的 Upgrade 请求；
- `WS_ALLOWED_ORIGINS` 仅用于明确列出的额外入口，不从任意请求头动态扩展；
- 更新极空间/反向代理部署文档和生产验收命令，删除与当前 HTTPS 入口冲突的说明。

前端连接提示规则保持保守：首次连接和短暂重连不显示橙色故障条；只有连续未完成房间同步达到降级阈值后，才显示“实时连接中断，已启用每 10 秒定期同步”。房间同步恢复后立即停止轮询并移除提示。

## 6. 结算流程与金额文案

### 6.1 三步流程

结算继续保留三步，因为服务器仍需保存草稿并生成带确认令牌的权威预览：

1. 带走金额；
2. 费用；
3. 核对。

第二步的主按钮改为“进入核对”。该操作先冲刷未保存草稿，再向服务器请求最新预览。核对页不显示“重新生成预览”。

核对页底部只保留两个动作：

- `修改`：返回费用步骤并使当前确认令牌失效；
- `确认结算`：直接调用永久结算接口。

不再显示“打开永久确认”，也不再弹出第二个永久确认对话框。不可逆说明以内联短文展示一次。提交中禁用两个按钮，防止重复点击。

如果提交时发生 `SETTINGS_VERSION_CONFLICT`，当前确认材料立即失效，页面返回费用步骤并提示“抽成规则已变化，请重新核对”。管理员再次进入核对即可获得新预览；这属于服务端并发保护，不恢复无意义的手动“重新生成预览”按钮。

### 6.2 金额显示规则

新增唯一的金额格式化规则，所有页面复用：

- 正数：`+¥1,700`
- 负数：`−¥1,700`，使用 Unicode 减号并把符号放在货币符号前
- 零：`¥0`

每位玩家的结算卡片按以下顺序显示：

1. `本局输赢`：使用带正负号的金额；
2. `房费`：显示无符号绝对费用，例如 `¥380`；
3. `其他费用`：仅在非零时显示无符号绝对费用；
4. `抽成`：显示无符号绝对费用；
5. 最终结果：
   - 正数为 `最终应收 ¥1,320`；
   - 负数为 `最终应付 ¥1,700`；
   - 零为 `最终收支 ¥0`。

最终结果永远使用绝对金额，因此不会再出现“应付 −¥1,700”。删除“费用后盈亏 · 抽成前应付”“结清 0”和括号内重复金额。计算字段仍保留在服务器 DTO 和测试中，只是不再用晦涩的中间会计语言占据主要 UI。

总买入、总带走、总房费和总抽成继续作为核对汇总展示，均采用统一货币格式。

## 7. 首页与历史战绩

### 7.1 首页收口

首页删除：

- “近 10 场最终金额”个人摘要；
- “最近战绩”区块；
- 对 `/api/history?limit=10` 的请求和旧 `HistoryGameSummary` 前端接口。

首页只展示当前进行中/结算中对局和管理员创建入口。用户通过固定“战绩”导航查看全部历史。

### 7.2 历史列表口径

历史列表 DTO 增加或明确当前用户在该局的 `myFinalAmount`：

- 普通用户只能收到自己参战的对局，因此显示本人最终金额；
- 管理员或超级管理员参战时显示本人最终金额；
- 管理员未参战时显示“查看明细”，不把全桌费用合计伪装成个人战绩。

列表金额使用 `−¥380` 格式。历史详情继续显示全桌不可变快照；硬删除是超级管理员专用的测试清理例外，不代表结算可编辑或重算。

## 8. 临时密码

前端定义单一常量 `DEFAULT_TEMPORARY_PASSWORD = '12345678'`，用于：

- 创建用户页的初始密码默认值；
- 重置密码对话框的新临时密码默认值。

输入框仍允许管理员修改为其他 8–128 位密码。后端不把 `12345678` 写死为唯一密码，只接收前端提交值。创建或重置后继续设置 `mustChangePassword=true`，用户首次使用临时密码登录后必须修改密码，现有会话撤销规则不变。

## 9. 头像体验与预设头像

### 9.1 预设头像资源

采用 DiceBear Lorelei 卡通风格，来源：

- https://www.dicebear.com/styles/lorelei/
- 该风格标注为 CC0 1.0。

实现时生成 12 个固定 seed 的静态头像并转换为本地 WebP，不在运行时请求 DiceBear。资源目录加入来源、生成版本、seed 和许可说明。

为避免历史快照外观漂移：

- 保留旧的 `preset-01` 至 `preset-12` 文件用于已有用户和历史记录渲染；
- 新头像使用 `preset-13` 至 `preset-24`；
- 头像选择列表只返回新的 12 个 ID；
- 新用户和管理员重置头像默认使用 `preset-13`；
- 共享契约继续接受旧 ID 作为可渲染历史值，但新选择请求只允许当前可选 ID。

### 9.2 选择与保存

认证会话用户 DTO 增加 `avatarKind` 和 `avatarValue`，个人页进入时能够显示真实当前头像，不再以 `null` 占位。

点击预设头像只改变本地“待保存”选择，并显示：

- 选中边框；
- `保存头像` 主按钮；
- `取消修改` 次要动作。

点击保存后才调用服务器；成功后更新会话内头像并显示“头像已保存”，失败则保留待保存选择和重试按钮。离线时保存按钮禁用。

### 9.3 从相册选择、裁剪与上传

原生 `<input type=file>` 保留为无障碍和系统相册入口，但在视觉上隐藏；可见控件改为统一样式的 `从相册选择` 按钮，并显示 JPG/PNG/WebP 与 5 MiB 限制。

选图后继续使用现有正方形裁剪：

- 默认居中裁剪；
- 可调整水平和垂直位置；
- 确认后生成 512×512 WebP，再由服务端验证并重编码为 256×256 WebP；
- 上传时显示百分比和进度条；
- 失败后保留原图与裁剪位置，显示 `重新上传` 和 `重新选择照片`；
- 成功前一直保留旧头像，成功后才替换。

## 10. 超级管理员全状态对局管理

### 10.1 管理页面

个人页的超级管理员管理区增加“对局管理”。新页面列出：

- 对局名称；
- 状态：草稿、进行中、结算中、已完成或已作废；
- 创建、开始或完成时间；
- 玩家人数；
- 进入现有牌桌/历史详情的链接（适用时）；
- `永久删除` 操作。

列表使用服务端分页并覆盖所有状态，使升级前遗留草稿也可被发现和删除。普通管理员和普通用户既看不到入口，也无法调用接口。

新增 `GET /api/games/manage?limit=50&cursor=...`，仅允许 `SUPER_ADMIN`。响应按创建时间和公开 ID 倒序排列，并返回不透明游标；客户端不在内存中拼接多个现有接口来猜测完整对局集合。

### 10.2 单次确认

点击“永久删除”只出现一个确认框，明确显示对局名称、当前状态和以下后果：

“购买记录、玩家锁、结算草稿、结算结果及费用分摊将一并永久删除，无法恢复。”

按钮文案为 `确认永久删除`。确认后直接执行，不再出现第二个弹窗。

### 10.3 硬删除接口和事务

新增 `DELETE /api/games/:id`，仅允许 `SUPER_ADMIN`。接口不接受客户端传入状态，不提供软删除选项。

事务步骤：

1. 取得生命周期协调锁，防止活动桌数量检查与删除交错；
2. 锁定目标 `games` 行；
3. 锁定并重新验证操作者仍为启用的超级管理员；
4. 保存最小必要的删除前审计快照；
5. 按外键依赖顺序删除：
   - `settlement_fee_allocations`；
   - `settlement_results`；
   - `settlements`；
   - `settlement_drafts`；
   - `buyin_events`；
   - `active_player_locks`；
   - `game_players`；
   - `games`；
6. 写入 `GAME_HARD_DELETED` 审计记录并提交。

删除不是把状态改为 `VOIDED`，数据库中不再存在对应 `games`、结算、购买或玩家行。审计日志只记录谁删除了哪个公开 ID、名称、原状态和时间，不参与业务查询，也不能恢复被删数据。

### 10.4 并发与实时行为

购买、结束、最终结算和硬删除都锁定同一对局行，因此同一时刻只有一个动作能够提交。删除活动或结算中对局后：

- 对应玩家的 `active_player_locks` 在同一事务中释放；
- 实时层向已加入房间的客户端发送 `game.deleted`；
- 客户端关闭购买、调整和结算界面，清理本地快照，返回首页并显示“该对局已由超级管理员删除”；
- 服务端清理该局内存观战状态。

如果删除请求重复到达，第一次返回成功，之后返回 `404 NOT_FOUND`；不会产生半删除状态。

## 11. 错误处理与安全

- 所有写按钮在提交期间禁用，防止重复动作。
- 原子创建、开始遗留草稿、结束、结算和删除都由后端权限与事务保证，前端隐藏按钮不是安全边界。
- 硬删除保留最小审计记录，但审计内容不得包含密码、Cookie、令牌、数据库连接或头像原文件。
- 生产 WebSocket 继续使用精确 Origin 白名单和会话 Cookie 鉴权。
- 头像继续执行客户端大小/类型预检和服务端真实格式、像素、尺寸、路径与重新编码验证。
- 设置版本变化时拒绝旧结算令牌；精简 UI 不削弱服务端并发校验。
- 可预期错误使用稳定错误码和可操作中文提示，未知错误不暴露内部堆栈。

## 12. 测试策略

实施采用测试先行，每个行为先增加失败测试。

### 12.1 共享契约与单元测试

- 新旧预设头像 ID 的兼容与当前可选范围；
- 认证用户头像字段；
- 历史个人金额字段；
- `game.deleted` 事件；
- `−¥X`、`+¥X`、`¥0` 和最终应收/应付绝对值格式；

## 13. 部署与兼容

## 14. 完成定义

只有以下条件全部满足才算完成：

1. 用户确认的 12 项改造都可从手机页面完成；

3. 创建和结算没有多余草稿、跳转或二次确认；

7. 单元、API、集成、端到端、类型检查、lint 和生产构建全部通过；
